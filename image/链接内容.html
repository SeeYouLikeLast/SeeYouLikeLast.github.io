基于Redis Lua脚本的分布式令牌桶限流实现

🔁 函数执行流程详解

  1. 线程安全初始化

    std::lock_guard<std::mutex> lock(mutex_);

    函数首先使用 std::lock_guard获取一个互斥锁。这是一个关键步骤，它确保了在同一个 RateLimiter实例上，同一时间只有一个线程能够执行这个 acquire函数。这对于防止多个线程同时修改本地状态（例如，虽然主要状态在Redis中，但锁能避免多个线程同时创建任务可能引发的混乱）是必要的。

  2. 创建Redis异步任务

    auto* task = WFTaskFactory::create_redis_task(redis_url_, 0, nullptr); std::string tk = "rate:" + key; std::string ts = tk + ":ts";

    这行代码通过工作流（Workflow）框架创建了一个访问指定 redis_url_的Redis异步任务。同时，它为传入的限流键（key）生成两个Redis键：- tk：用于在Redis中存储该键对应的当前令牌数量。- ts：用于存储最后更新令牌数量的时间戳。

  3. 设置Lua脚本执行命令

    task->get_req()->set_request("EVAL", { lua_script, "2", tk, ts, std::to_string(rate_), std::to_string(capacity_), std::to_string(time(nullptr)) });

    这是核心配置步骤。它向Redis任务发送一个 EVAL命令，用于执行预定义的Lua脚本（lua_script）。后面的参数含义如下：

    • "2"：表示后面紧跟着的两个键（tk和 ts）是作为 KEYS数组传递给Lua脚本的。
    • tk, ts：即上面生成的键名。
    • rate_, capacity_：令牌生成速率和令牌桶的最大容量。
    • time(nullptr)：当前的UNIX时间戳（秒为单位）。
      Lua脚本会在Redis服务端原子性地执行令牌计算和扣减逻辑，最终返回1（允许）或0（拒绝）。

  4. 设置回调函数与同步等待

    WFFacilities::WaitGroup wg(1); bool allowed = false; task->set_callback([&wg, &allowed](WFRedisTask* t) { auto* resp = t->get_resp(); if (resp->get_result() == REDIS_REPLY_INTEGER && resp->get_integer() == 1) allowed = true; wg.done(); }); series_of(task)->start(); wg.wait();

    这部分是异步执行的核心。

    • 创建一个计数器为1的WaitGroup（wg）用于同步等待。
    • 设置任务的回调函数。当Redis服务器返回结果后，该函数被调用。它检查Redis的回复：如果回复类型是整数（REDIS_REPLY_INTEGER）且值为1，则将本地变量 allowed设置为 true，表示请求被允许；否则保持 false。最后调用 wg.done()通知等待的线程。
    • series_of(task)->start()将任务提交到工作流引擎开始异步执行。
    • wg.wait()会使当前线程阻塞，直到回调函数中执行了 wg.done()才继续往下执行。这样就完成了异步转同步的操作。

  5. 返回最终结果

    return allowed;
    函数返回回调函数中设置的 allowed值。

⚖️ 设计特点与考量

  • 同步阻塞接口：尽管内部使用了异步任务，但通过 WaitGroup的等待，acquire方法提供了一个同步阻塞的接口给调用方。调用者会等待直到拿到限流结果。

  • 潜在的锁竞争：函数开头的互斥锁（mutex_）保证了单实例下的线程安全，但在超高并发场景下，它可能成为性能瓶颈，因为所有线程需要串行化地创建和等待Redis任务。

  • 超时处理的缺失：当前实现中，wg.wait()会一直等待直到Redis返回结果。在实际生产环境中，通常需要增加超时机制，防止因网络问题或Redis故障导致线程无限期挂起。

位图

Redis 使用了一种称为“位图”的紧凑数据结构来高效表示槽位分配信息。

计算步骤 说明 数值与公式
1. 确定槽位总数​ Redis 集群固定将数据空间划分为 16384 个槽位。 16,384 个
2. 位图的基本单位​ 位图使用比特位来表示每个槽位的状态（例如，1表示该节点负责此槽位）。每个槽位仅需 1个比特。 1 bit/slot
3. 计算所需总比特数​ 槽位总数 × 每个槽位占用的比特数。 16,384 slots × 1 bit/slot = 16,384 bits​
4. 将比特转换为字节​ 1 字节等于 8 比特。 16,384 bits ÷ 8 bits/byte = 2,048 bytes​
5. 将字节转换为千字节​ 1 千字节等于 1024 字节。 2,048 bytes ÷ 1024 bytes/KB = 2 KB

Redis Lua脚本

1. 参数获取与初始化

  • 作用：脚本首先接收两个Redis键（KEYS）和三个参数（ARGV）。这些参数定义了令牌桶的基本属性。

  • 键的设计：使用两个键分离存储令牌数和时间戳，避免数据覆盖，是常见的Redis限流模式。

2. 令牌桶的初始化

  • 作用：检查令牌桶是否存在。如果不存在（如首次请求或键已过期），则进行初始化。

  • 初始化逻辑：

    • 将令牌数设为最大容量（capacity），实现”冷启动”时桶满的状态。
    • 同时记录当前时间戳为最后一次刷新时间。
    • 为两个键设置120秒的过期时间（expire 120），防止不活跃的键长期占用内存。这个过期时间应大于令牌桶的自然填充时间。

3. 令牌的计算与补充

  • 核心逻辑：这是令牌桶算法的关键步骤，通过计算而非定时任务来补充令牌，更高效。

  • 计算过程：

    1. 计算时间间隔：(now - last_timestamp)，即距离上次刷新经过的秒数。
    2. 计算应补充的令牌数：时间间隔 × 速率。例如，速率=2令牌/秒，间隔=3秒，则补充6个令牌。
    3. 计算最新令牌数：剩余令牌 + 补充令牌，并确保不超过桶容量（math.min的作用）。

4. 时间戳更新与决策

  • 时间戳更新：无论请求是否通过，都将时间戳更新为当前时间。这确保了下次计算时时间基准正确。

  • 决策逻辑：

    • 如果剩余令牌数 ≥1：消费一个令牌（decr），返回1（允许）。
    • 如果剩余令牌数 <1：不消费令牌，返回0（拒绝）。这意味着当前请求无法获取令牌。

原子性

原子性指脚本作为一个整体执行：期间不会被其他命令插入，所有操作要么全部完成，要么全部不完成。
