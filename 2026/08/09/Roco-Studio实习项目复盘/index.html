Roco Studio 实习项目复盘：从 AMR 接口适配到地图导航

发表于2026-08-09|更新于2026-08-09|项目实践
|浏览量:

Roco Studio 是我在实习期间接触的工业机器人工作站管理与控制平台。它需要把机械臂、AMR、相机等不同设备接入同一套系统，并在 Web、桌面端和平板端完成设备管理、状态监控、任务编排与运行控制。

本文前半部分介绍完整平台，后半部分重点复盘我实际负责的 AMR 地图、点位、遥控与导航业务。项目中的机械臂、相机、程序编排和多端交付等模块属于平台整体能力，不代表全部由我完成。文章只讨论可以公开的技术架构和工程经验，不涉及客户信息、生产环境地址、账号凭据与私有协议细节。

项目要解决的问题

传统工业设备通常拥有不同的 SDK、通信协议和状态模型。如果界面直接绑定某一种设备，后续增加设备类型时会产生大量重复开发。Roco Studio 的目标是建立一层统一的设备抽象，让上层应用围绕“设备、点位、程序、任务”组织业务，而不是直接处理每个厂商的底层接口。

平台主要覆盖以下场景：

  • 管理 Elfin 机械臂、Ego AMR、Roco FAIO 与工业相机等设备。
  • 查看设备状态，执行点动、位置控制、I/O 监控与参数配置。
  • 构建地图并完成移动机器人的导航与点位管理。
  • 通过可视化方式编排程序，安装业务插件并调度生产任务。
  • 在浏览器、Electron 桌面端和 Android 平板端复用同一套核心能力。

整体架构

前端负责交互和实时状态展示；FastAPI 提供设备、数据库、Redis 与对象存储相关的 HTTP 接口；MQTT 网关作为 ROS 2 节点运行，在 MQTT 消息和 ROS 2 Topic/Service 之间转发；底层驱动再把统一的 JSON-RPC 请求映射到实际设备 SDK。

技术栈

我的实际工作范围

我于 2025 年 12 月至 2026 年 3 月在陕西伏羲启源科技有限公司担任后端开发实习生，主要工作并不是介绍或维护整个 Roco Studio 平台，而是围绕 AMR 小车的地图、点位、遥控和导航，完成设备接口适配、前后端链路联调、数据持久化以及可视化控制页面开发。

我主要修改的代码集中在两个位置：

  • packages/drivers/roco_faio_driver/src：C++/ROS 2 设备驱动、JSON-RPC 方法分发、底盘 WebSocket 协议适配、点位数据管理和导航控制。
  • client/web/src：AMR 遥控、实时地图、建图和导航页面，以及 MQTT 命令与事件处理。

设备接口适配与全链路联调

我完成了 AMR 底盘主要业务接口的适配与调试，包括设备状态、建图与地图保存/切换/删除、Marker 管理、激光定位、遥控、单点与多点导航、停止任务、充电和急停等能力。

驱动层使用统一的方法映射表接收上层 JSON-RPC 请求，再根据底盘协议组装命令，通过 WebSocket 下发并等待响应。返回结果会被转换为统一的成功或错误结构，供上层继续处理。联调过程中还需要处理接口超时、参数校验、错误码透传、地图 Base64 数据的新旧协议兼容，以及设备断线后的状态恢复。

这项工作的重点不是单独写一个接口，而是确认请求参数、协议转换、设备响应、异步事件和页面状态在整条链路上保持一致。

实时地图与导航控制页面

我使用 Vue 3、Element Plus 和 Leafer UI 实现并完善 AMR 的建图与导航页面。页面通过 MQTT 下发建图、保存地图、切换地图、点动和导航等命令，同时订阅地图、位置、路径和任务状态事件。

实时地图页面需要同时处理栅格地图和动态元素：

  • 根据地图的分辨率、宽高和原点，将世界坐标转换为画布坐标。
  • 支持地图缩放、平移、旋转和视图复位，并保证鼠标选点在变换后仍能得到正确坐标。
  • 在地图上叠加小车位姿、运行轨迹、规划路径、导航点、固定路线和区域信息。
  • 将建图、地图保存/切换、遥控、目标点选择、开始/暂停/停止导航等操作集中到同一控制页面。

这部分工作让我处理了一个很典型的工程问题：后端使用机器人世界坐标，地图使用栅格坐标，浏览器画布又有缩放、偏移和 Y 轴方向差异。只有统一坐标转换，地图点击位置、点位存储位置和底盘导航目标才能真正对应起来。

点位与路线数据持久化

为了让地图上的业务点位能够长期维护，我使用 PostgreSQL 完成了点位类型、地图点位、固定轨迹点和区域数据的增删改查。接口使用参数化 SQL，并围绕地图名称、点位类型、坐标、朝向和轨迹顺序等字段进行校验与查询。

前端获取点位列表后在地图中渲染标记，用户可以记录小车当前位置、编辑点位或选择目标点发起导航。这样，数据库中的业务点位、页面上的可视化标记和底盘接收的导航目标形成了闭环，而不是只在页面内保存一份临时坐标。

导航状态机与路径规划调试

遥控和导航都会向底盘发送运动命令，如果二者缺少互斥和切换规则，就可能出现命令竞争。我参与实现并调试了 AMR 运动状态管理，将运动过程划分为 IDLE、REMOTE_CONTROL、NAVIGATING 和 ERROR 等状态，并通过独立工作线程执行导航任务，支持任务取消、失败重试、软急停和人工接管。

在导航链路中，我参与了以下算法和策略的实现与调试：

  • 使用 OpenCV 按小车半径与安全余量对障碍栅格进行膨胀，避免规划路径贴近障碍物。
  • 构建距离场，在 A* 的路径代价中增加近障惩罚，引导路径远离障碍区域。
  • 使用八邻域 A* 生成全局路径，再通过 Floyd 可视性优化减少冗余折点。
  • 对优化后的路径进行航点采样，并根据相邻航点计算运动朝向后依次下发。
  • 针对起点或终点落入膨胀区、目标不可达、导航卡顿、终点姿态偏差等问题进行日志分析和现场联调。

这些工作使导航功能从“能够发送目标点”推进到“能够规划、执行、暂停、接管并反馈结果”的完整业务流程。

核心模块

设备管理与控制

设备页不是简单展示一张列表，而是为不同设备提供相应的控制面板。机械臂需要关节/笛卡尔控制、速度设置、点位记录和 I/O 监控；AMR 需要地图、导航、位置与任务状态；复合机器人还要协调移动底盘与双机械臂。

前端按设备类型拆分页面和组件，驱动层则通过统一 JSON-RPC 格式暴露命令。这样既保留了设备的差异化能力，也让上层调用方式保持一致。

MQTT 与 ROS 2 桥接

系统同时存在同步命令和异步状态两类数据：

  • 需要明确结果的控制指令走 ROS 2 Service，并通过 JSON-RPC id 关联请求与响应。
  • 日志、事件和设备状态走 ROS 2 Topic，再通过 MQTT 推送给订阅端。
  • Redis 保存主题映射等高频状态，PostgreSQL 保存需要长期维护的业务数据。

这条链路把浏览器友好的 MQTT 与机器人生态常用的 ROS 2 连接起来，前端无需直接理解 ROS 2 的运行环境。

驱动与多实例隔离

机械臂驱动将厂商 SDK 封装为 ROS 2 服务和主题，并使用可配置的主题前缀隔离多个实例。例如，不同机械臂可以拥有独立的命令、日志和事件通道，避免同一工作站内名称冲突。

设备连接还需要处理自动重试、超时、断线恢复和降级运行。服务启动时会分别检查 MQTT、Redis 与数据库状态，让非关键依赖暂时不可用时仍能保留部分能力。

程序、插件与任务

程序编排负责描述一组可执行步骤，插件把具体工艺封装为可复用能力，任务调度则把程序与设备、时间和运行状态关联起来。项目中包含壳体转运、装配和涂胶等工艺插件，体现了“平台能力 + 行业插件”的扩展思路。

实习中的工程体会

先划清系统边界

前端、消息网关、ROS 2 服务和设备驱动各自解决不同问题。联调时按照 MQTT 请求、ROS 2 服务、JSON-RPC 分发、WebSocket 报文和设备响应逐层排查，比只看页面报错更容易定位问题。

实时系统必须面对异常

工业现场的网络、设备和中间件都可能短暂不可用。连接重试、周期状态查询、命令超时、状态回传和异常停止不是附加功能，而是控制系统能够稳定运行的基础。

可视化必须与真实坐标一致

地图页面看起来是前端展示，实际上依赖地图元数据、坐标系、设备位姿和导航协议的共同约定。坐标转换只要在原点、分辨率、缩放或 Y 轴方向上出现一次偏差，就会表现为小车图标漂移、点位错位或导航目标错误。因此，可视化本身也是控制链路的一部分。

项目总结

Roco Studio 让我第一次从完整链路理解工业软件：页面上的一次点击，会经过 MQTT、ROS 2 网关、JSON-RPC 方法分发和设备驱动到达真实底盘，最终再沿事件链路返回界面。我的实际工作覆盖了 AMR 接口适配、实时地图、点位存储、遥控页面和导航功能，也让我理解了跨语言、跨进程和跨设备协作时，如何设计可调试、可恢复且状态一致的控制链路。
