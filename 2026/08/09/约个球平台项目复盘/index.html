约个球：球类运动生活服务平台项目复盘

发表于2026-08-09|更新于2026-08-09|项目实践
|浏览量:

“约个球”是一个面向羽毛球、乒乓球、足球、篮球、网球和排球等运动的移动端生活服务平台。项目把找场所、购买团购、装备商城、同城约球、球友社区和 AI 推荐组织成一条完整的演示链路。

当前项目用于学习与功能演示：支付为模拟支付，真实场所来自高德 POI，团购、库存、订单、评价和社区内容由平台本地数据维护。它不代表已经具备商业系统所需的支付合规、高可用、灾备与容量保障。

功能设计

场所、团购与装备

首页优先使用浏览器定位，通过高德地图搜索附近真实运动场所，并提供逆地理编码、距离和场所详情。平台本地维护场馆团购、装备商品、库存、购物车、订单与评价数据，使用户可以从发现地点继续完成购买和约球。

同城约球与社区

用户可以按运动类型、时间、水平、人数和场所筛选活动，也可以发起或加入活动。社区支持发布动态、上传图片、关联团购或商品、点赞、关注、个人主页和关注 Feed，把交易场景与球友关系连接起来。

AI 助手

AI 助手不直接凭模型记忆回答商品和场所信息。后端工具先查询真实业务数据，完成候选过滤与结构化排序，再让模型解释推荐理由并返回可操作的业务卡片。涉及“购买后发起约球”等连续操作时，系统会先向用户二次确认。

这种 Grounding 方式让大模型负责语言理解和推荐解释，让数据库继续作为事实来源，降低推荐不存在商品或错误场所的概率。

关键工程设计

登录与唯一性校验

平台支持邮箱验证码登录、自动注册和密码登录。登录态使用 Redis Token 保存，并通过 Token 刷新拦截器和登录拦截器完成续期与接口保护。邮箱、用户名等字段先由布隆过滤器进行快速预判，再使用 MySQL 唯一索引做最终一致性兜底。

缓存治理

不同问题采用不同策略：缓存空值防止不存在数据反复穿透；TTL 加随机值降低同一时间大量失效造成的雪崩；热点秒杀活动使用逻辑过期降低缓存击穿风险；地图逆地理编码则使用短 TTL，平衡实时性与外部 API 调用次数。

高并发秒杀

秒杀链路由多层约束共同保证：

  1. Redis Lua 在一次原子操作中完成活动校验、库存判断和预扣。
  2. Redisson 分布式锁控制同一用户的并发请求。
  3. 一人一单规则与数据库唯一索引防止重复订单。
  4. RocketMQ 将订单异步落库，削减高峰期数据库压力。
  5. MQ 未部署或投递失败时降级到同步事务，保证演示环境仍能完成下单。

Feed 流的推拉结合

普通用户发布动态时采用推模式，把内容写入关注者收件箱，读取速度快；关注者很多的大 V 改用拉模式，避免一次发布产生过大的写扩散。读取关注流时再合并两类来源，在用户体验和系统成本之间取得平衡。

文件与访问边界

MySQL 只保存文件元数据，MinIO 保存文件本体。上传时校验类型和大小，删除时校验文件所有者；公开头像和动态图片由 Nginx 的对象路径直接访问。当前公开 Bucket 适合演示素材，不适合任何私密附件，商业化前必须拆分访问策略。

部署与验证

开发环境通过 Docker Compose 启动 MySQL、Redis、RocketMQ 和 MinIO，后端运行在 8088，Vite 开发服务器运行在 5173。生产环境由 Nginx 托管前端并反向代理 /api 与 /objects，Spring Boot 使用 systemd 守护。

项目在 2 GB ECS 上提供 prod,lite 配置，默认不启动 RocketMQ，以较低资源运行核心演示链路；完整环境仍保留异步秒杀能力。截至 2026-08-03 的最终演示版记录中，后端 50 个自动化测试通过，前端类型检查和生产构建通过。

项目收获

这个项目最有价值的地方不是简单堆叠功能，而是把多个典型后端问题放进同一个业务闭环：认证、缓存、秒杀、消息队列、对象存储、Feed 流、地图服务和 AI Agent 彼此关联。开发过程中需要同时考虑正常路径、失败降级、数据一致性和部署资源限制，也让我更清楚地认识到“演示可交付”与“商业生产可用”之间的工程差距。
